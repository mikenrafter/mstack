# Residual and reviewer-note integration

Inspected on 2026-11-10. This is a design proposal based on local source, not an implementation or a runtime validation. Repository paths below are relative to `/home/mini/Documents/repos/residual` unless another root is given. The earlier reports remain unchanged.

## What residual does today

Residual is a Rust CLI for practicing Barry O'Reilly's Residuality Theory with a coding agent as a Socratic partner. The operator records architectural pressures and possible changes. The CLI stores and checks that model, calculates coupling summaries, and supplies agent prompts. `README.md`, `ARCHITECTURE.md`, `src/cli.rs`, and `src/skills/mod.rs` describe and implement this workflow. Residual adds purposes alongside the theory's stressors and calls both forces.

A force has a shortname, description, naive change, outcomes, and attractor reference. Attractors describe recurring states with positive and negative sides. Components have names, status, and architecture-set membership. Residues connect forces to components; the v4 `residues.csv` matrix is the coupling source. Lexicon entries give shared terms and aliases. See `src/structure/analysis/force.rs`, `src/structure/analysis/attractors.rs`, `src/structure/analysis/residues.rs`, `src/structure/definition/components.rs`, and `src/storage/format.rs`. A whole-system residue can represent a process, policy, organizational, or hardware response.

Inputs include operator-authored records, Markdown personas and research notes, iteration snapshots, source-comment tags, and Git state. Metadata can live inline or on a Git sidecar branch, with optional per-code-branch metadata. This checkout's working `residual/` contains only `config.toml`; its ledger is available under `origin/residual/metadata:residual/`. `src/storage/git_sidecar.rs` owns that storage mechanism. `src/verify.rs` checks outcome vocabulary and links, and warns about dangling tags. These checks do not establish that claimed behaviors work.

Findings reach agents through `residual skill data`, and people through CLI tables and HTML. `src/skills/context.rs` assembles context for optional walks, integration, FMEA, and ATAM. `src/nkp/` calculates matrix metrics and fusion/fission suggestions. `src/view/snapshot.rs` merges committed and working metadata; `src/view/static_export.rs` renders it. The current branch adds bundle, heatmap, and region views in `web/src/nkp-landscape.ts`. Browser edits stage CLI commands for an operator to execute. `residual serve` serves a startup snapshot, not a continuously refreshed ledger. There is no implemented PR reviewer, model council, semantic code-diff engine, or reviewer-preference reader in the inspected CLI and skill registry.

## Reviewer-note discovery and ownership

The source practice is `/home/mini/.claude/skills/build-loop/references/reviewers.md`. Its four kinds are explicit requirements, observed examples, owner observations, and uncertain inferences. Contributor guides, PR templates, CI rules, and review policy outrank examples. Direct requests apply to their stated PR and scope. An owner observation is attributed guidance, even when it contains a number.

Add a read-only `residual review brief` command. Its proposed options are repeatable `--reviewer`, optional `--pr`, optional `--notes-dir`, optional `--project` for the contribution target identity, and `--format markdown|json`. An optional `--base` and `--head` identify the code under review; resolve supplied revisions once to full commit IDs. Without them, record the current head and explicitly say the review base is unspecified. Do not fetch, inspect remote comments, launch agents, or assess code while building a brief.

Default discovery uses `<project>.research/review/` beside the main project checkout. Read `<reviewer>-review-preferences.md` and, if present, `<project>-contributing.md` for project-wide requirements. Resolve the project from the Git top level, not the invocation directory, residual's metadata cache, or its sidecar branch. For linked worktrees, use the common repository's main checkout as the default naming anchor. If that anchor cannot be resolved, report ambiguity and require `--notes-dir`; do not search neighboring projects. An explicit directory replaces the default. Sort files and items deterministically.

Match reviewer names exactly to safe file stems. Without `--reviewer`, list available reviewers and include only the project-wide file; do not combine every maintainer's preferences into mandatory policy. A changed reviewer rebuilds the brief without carrying over the prior reviewer's checks. Match any recorded project identity against the selected project's normalized Git remote identity. A renamed checkout can use `--notes-dir`; matching directory names alone does not prove repository identity. Fork contributions need the target project identity stated explicitly when origin differs.

Absent notes produce `coverage: missing`, their expected path, and no invented preferences. An explicitly requested missing reviewer file, unreadable file, or invalid structured item produces `coverage: partial` with a precise diagnostic. A missing default directory is an ordinary empty-input state. Reject reviewer path traversal and symlinks that escape the selected notes directory. Read a bounded set of Markdown files; report any size limit or omission. Never rewrite, migrate, or create notes during discovery.

Keep these files in the sibling research directory. `src/skills/research.rs::save` currently writes notes into residual metadata, and `src/storage/research.rs` re-exports it. Neither is a reviewer-policy reader. Do not copy preferences into that storage or into the defense ledger. If a walk suggests a genuine process residue, the operator can separately approve capturing it through existing CLI commands.

## A small parse contract

Use ordinary Markdown list items beginning with exactly one visible label: `- Explicit requirement:`, `- Observed example:`, `- Owner observation:`, or `- Uncertain inference:`. Keep the claim in prose and source links in ordinary Markdown. Indented continuation lines belong to the item. Ignore candidate labels inside fenced code or quoted examples. Headings organize the document but do not assign authority to unlabelled paragraphs.

Structured metadata is optional for guidance. An eligible requirement also needs one trailing JSON comment named `residual-review-v1`. This uses the existing `serde_json` dependency and avoids introducing a general YAML parser. For example, the following is an illustrative fixture, not a statement about residual's own contributor policy:

```markdown
- Explicit requirement: Keep regression tests with the behavior they establish. [Guide](CONTRIBUTING.md#tests).
  <!-- residual-review-v1 {"id":"tests-with-behavior","project":"github:example/project","reviewer":"maintainer","scope":{"kind":"repository"},"checked":"2026-11-10","sources":[{"href":"CONTRIBUTING.md#tests","kind":"guide","dated":null,"sha256":"<complete-file-digest>"}]} -->
- Owner observation: The owner reports a warning range around 6,000 to 8,000 changed lines. This is guidance.
- Uncertain inference: Smaller concern-specific changes may receive quicker review. No size ceiling is established.
```

The comment schema defines `id`, `project`, `reviewer`, `scope`, `checked`, and `sources`. IDs are unique within a file and stable across wording edits. Scope is one of repository, PR with an exact URL, or paths with explicit relative globs. A path-scoped requirement remains potentially applicable if changed paths are unavailable. Sources have a link, a kind, a nullable publication date, and a content digest when the source is a local file. Supported authoritative source kinds are guide, template, CI, review-policy, and direct-request. A direct request requires a PR scope. Owner observations also record who reported them and when; missing attribution remains visible as incomplete guidance.

Dates use `YYYY-MM-DD`. `checked` records when the curator checked the claim against its sources; it is distinct from the source's publication date. Relative source paths resolve against the project root, not the notes directory. They cannot escape that root. PR links remain exact comment/review permalinks. A source from another project can support an observed example, but cannot establish a requirement in this one. For a direct request, the curator must preserve the actual instruction and its scope; a label is an assertion of provenance, not independent proof that the linked text says it.

An optional file-level `residual-review-file-v1` JSON comment holds `policy_checked` and `policy_inventory`. The inventory is a list of project-relative paths with `present` and nullable `sha256` fields, covering both the consulted files and expected-but-absent policy locations. It is written during research, not by the brief reader. Without this baseline, explicit items can load but need revalidation before entering the current required checklist. The item example above omits that file-level baseline. This keeps old prose readable while making a guide-change check reproducible.

Only a correctly labelled, sourced, applicable explicit requirement can become a required checklist item. Missing metadata, an unknown source kind, duplicate IDs, invalid dates, an unsupported comment version, or a conflicting label produces a diagnostic and a visible unvalidated item. It never falls back to an enforceable requirement. Reject unknown authority-changing fields such as `blocking` or `severity`; source text cannot choose execution behavior. Guidance does not acquire authority by sharing a URL with a requirement. Two items with conflicting instructions stay separate and require resolution.

Backward compatibility means the existing Abdul file loads unchanged and remains useful. Its `Research date: 2026-11-10` is a document research date. Its paragraph beginning `Owner observation, 2026-11-10:` is owner guidance. Its linked case bullets are displayed as legacy examples. Its unlabelled practical rules and concluding checklist are shown verbatim under legacy guidance with `classification: unverified`. Preserve their Markdown and source locations without using a language model to classify them as policy. No part of that file enters the required checklist until a curator labels and scopes an actual explicit requirement. In particular, the six-part request on edge #669 is a case about that PR; it does not impose six-part stacks on future contributions.

## Checklist and council output

Introduce a deep read-only module at `src/review/mod.rs`, with internal parsing and brief-building code in `src/review/notes.rs` and `src/review/brief.rs`. Proposed types are `NoteKind`, `ReviewerNote`, `NoteProvenance`, `RequirementScope`, `SourceRef`, `Freshness`, `NotesLoadReport`, `RequirementCheck`, and `ReviewBrief`. Keep provenance and diagnostics in the normalized result. A private constructor creates an eligible requirement only after kind, source, scope, and freshness checks. Guidance types have no blocking flag or conversion based on numeric text.

`ReviewBrief` has separate collections for required checks, observed examples, owner observations, uncertain inferences, legacy guidance, and items needing revalidation. Every item carries its kind even when a renderer flattens those collections. A stale explicit requirement remains identified as explicit and unresolved in the revalidation collection. It cannot disappear into ordinary guidance or count as satisfied.

Markdown starts with the target project, selected reviewers, PR if supplied, code revisions, notes digests, and coverage. Each applicable current requirement becomes an unchecked line with a stable key such as `reviewer/filename#tests-with-behavior`, its exact scope, and source links. In a review result, the allowed answers are satisfied with evidence, violated with a concrete counterexample, not applicable with a reason, and unchecked. Revalidation is a separate unresolved state. A missing answer, timeout, or stale source is never a pass.

Observed examples and owner observations appear in visibly labelled guidance sections without task checkboxes. Inferences appear under uncertain inferences with an explicit statement that they cannot establish policy. Preserve numeric ranges as quoted text. Do not derive a limit, split count, architecture score, or approval condition from them. The brief builder does not execute checks, calculate a compliance score, or alter `residual verify all`. The external orchestrator may block approval on a demonstrated violation of an applicable explicit requirement. It must resolve check IDs against the typed required collection, so a response citing a guidance ID cannot become a policy blocker.

An external build-loop or council receives the same pinned brief in every review tier. Ask each reviewer to return the requirement ID, disposition, evidence, and unresolved assumptions. Keep independently discovered correctness findings separate from preference compliance. A real bug supported by code remains a bug even if no preference mentions it. A suggestion justified only by an inference cannot be relabelled a requirement violation. Scores and reviewer agreement do not change a note's authority.

Wire `Command::Review` and `ReviewOp::Brief` through `src/cli.rs` and declare the module in `src/main.rs`. Keep process text beside the clap action, following `ARCHITECTURE.md`. Add a review configuration section through `src/storage/config.rs` and the runtime `src/config.rs` parsing path for the notes-directory override, project identity, and refresh interval. Test that path because the existing `parse_any` constructs a legacy runtime `Config` from selected storage fields. Do not add a separate verification-config module.

For optional skill integration, extend `src/skills/phases.rs::data`, `src/skills/mod.rs::data`, and `src/skills/context.rs::build` with an optional selected review context. Append the same rendered brief when a reviewer is selected, initially for ATAM and tdd-implement. Keep it absent from ordinary walks unless requested. Reviewer-brief generation must work with an uninitialized residual ledger; it does not need attractors, personas, or bootstrap approval. `Persona` remains unchanged. A future embedded review skill would need registration in `SKILLS`; no such skill exists today.

Ship CLI/JSON first. A later `view --reviewer` option can add an optional `review` section to `LandscapeSnapshot` in `src/view/snapshot.rs`, rendered by a new `src/view/components/review.rs` through `src/view/static_export.rs` and `src/view/shell.html`. ## Staleness, precedence, and provenance

Capture a content digest for every notes file and every locally consulted policy file. Record a policy inventory including contributor guides, applicable PR templates, CODEOWNERS, CI definitions, and explicitly referenced policy documents. Record both presence and absence, so adding a new guide invalidates an old inventory. The curator records which policy paths were checked and when. A loader can compare current local contents with that snapshot; it cannot infer that an omitted policy was reviewed.

Mark notes as needing refresh when the reviewer changes, the configured refresh interval elapses, or the policy inventory changes. Proposed default is 90 days, configurable as a research cadence, not a contribution size rule. Independently mark a claim for revalidation when a cited source's digest changes, its checked date is missing, or its scope cannot be resolved. A local versioned policy may have no publication date when its digest and check date are known; an undated external claim needs revalidation. A dated external comment can be shown offline, but its current availability and continuing applicability remain unverified. File modification time and a new report-generation time do not renew research dates.

A contributor-guide change after the notes' checked date requires refresh even if the changed passage looks unrelated. A digest mismatch requires refresh even when Git history or dates are unavailable. Until refreshed, preserve explicit requirements as unresolved obligations and link the currently available guide. Do not silently enforce an old paraphrase or claim the contribution is compliant. Current applicable repository policy takes precedence over reviewer examples and over superseded requests. If two explicit sources conflict and no recorded supersession resolves them, show the conflict for the owner; timestamps alone do not decide authority.

The review manifest pins notes bytes, parser version, policy digests, selected reviewer, project/PR scope, code base/head, and any dirty inputs. Build it from captured bytes once. If inputs change during collection, report a partial result and require regeneration. Later review tiers compare those pins before reusing a brief. Edited notes invalidate earlier dispositions; deleted files remain represented as missing sources in an archived brief. An export contains the normalized records and provenance needed to interpret that historical brief, while preserving its stale state.

Each displayed claim links back to the local notes path and line range, the file digest, and its original public source or local policy anchor. For locally versioned sources, also record commit and blob identity when available. A content digest supports comparison even when notes are untracked. Keep attribution, source publication date, research date, and last validation date distinct. An unavailable source remains visible with a diagnostic. No normal read operation fetches it.

Treat notes as quoted research data when composing agent prompts. A source paragraph cannot issue tools, authorize writes, or change the four-kind contract. In an HTML panel, render escaped text and allow only safe source-link schemes; do not execute embedded HTML. Publishing a private notes file is a separate owner decision. Existing defense routing in `src/structure/analysis/outsiders.rs` does not make reviewer notes public or authorize outreach.

## Red tests for a build-loop implementation

Use small committed fixtures, including a preserved copy of the current Abdul file with its capture date. Derive expectations from this contract, not generated output. Co-locate parser tests with the module, use CLI integration tests for discovery and exit behavior, and add Rust/TypeScript parity fixtures only if the UI phase is built. Each test names its RV claim and the broken behavior it rejects. The red phase should establish behavior failures through the intended entry points, rather than treating missing imports as proof.

Seed a decoy neighboring project and assert its text never enters the brief. This catches discovery based on current directory or residual's metadata cache.

RV2. Exact reviewer selection includes that reviewer and project-wide notes only. Changing reviewers removes the first reviewer's checks. An origin/target identity mismatch is reported, and a PR-scoped request is absent from unrelated PR checklists. This catches accidental global policy aggregation and cross-project leakage.

RV3. A literal four-kind fixture produces exactly one item of each kind and one eligible requirement. Markdown and JSON preserve the kind, text, scope, dates, and provenance. A label inside a fenced example or blockquote creates no requirement. This catches prose heuristics and renderer promotion.

RV4. The unchanged Abdul fixture yields zero required checks. Its owner observation, linked examples, practical advice, numeric warning range, and source locations remain visible as guidance. RV6. Missing provenance, a duplicate ID, malformed JSON, an unknown version, an invalid date, and an attempted `blocking: true` on guidance produce visible diagnostics without an eligible requirement. Other valid items still render. This catches permissive fallback and whole-file data loss.

RV7. A requirement applying only to one PR cannot block another PR. A path-scoped requirement with unknown changed paths remains unresolved rather than satisfied or silently omitted. A direct request without PR scope is unvalidated. This catches overgeneralized reviewer instructions.

RV8. With an injected date, the default 90-day refresh boundary is deterministic. Missing and future dates produce diagnostics. Changing a contributor guide, adding a previously absent guide, or changing policy content with an unchanged timestamp requires refresh. RV9. A stale explicit requirement remains visible as needing revalidation and cannot count as satisfied. This catches silent policy deletion and newest-date-wins resolution.

RV10. Missing default notes, an explicitly requested missing file, an unreadable file, an oversized file, and a mid-read edit have distinct coverage/diagnostic results. RV11. Build a brief twice from identical captured inputs and compare stable item order, IDs, and digests. RV12. CLI, skill-context integration, and JSON use the same required/guidance partition. An external review response that cites a guidance ID as a requirement violation is rejected as such. RV13. For a read-only run, compare source file bytes, directory entries, Git refs, and ledger contents before and after. ## Questions for the owner and proposed defaults

Should residual execute a council or prepare its context? Default to a read-only brief for the existing external build-loop. Council execution, scoring, and persisted adjudication remain separate work.

Which requirements may block a contribution? Default to applicable, sourced explicit requirements, with a reviewer supplying evidence of a violation. Residual's structural verification and commit hooks gain no preference gates. Missing or stale evidence remains unresolved and never implies approval.

How should old notes be upgraded? Default to lossless advisory loading. A curator can add labels and metadata during a later research pass. Do not auto-promote the Abdul checklist or infer a numeric ceiling.

Which project identity and directory should a fork or renamed checkout use? Default to the sibling directory anchored to the main checkout and the explicitly selected contribution target. Require an override when identity is ambiguous. Do not guess across sibling repositories.

How often should observations be researched again? Default to 90 days, and immediately after a reviewer or contributor-policy change. Treat this as a refresh reminder. Keep source dates and changed-content checks independent of it.

Should reviewer notes appear automatically in architecture walks or browser exports? Default to explicit reviewer selection, CLI and JSON first, with ATAM/tdd-implement context opt-in. Add the read-only HTML panel only if the owner wants it. Keep ordinary force/coupling views unchanged.

Should reviewer preferences become residual forces or personas? Default to keeping them external context. An operator may separately capture a justified process residue with a provenance link, through the existing approved CLI write path.

Should remote sources be refreshed automatically? Default to offline reads and explicit revalidation diagnostics. Source gathering, edits to notes, and any publication or outreach require a separately authorized task.
